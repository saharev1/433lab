Причина не в nginx и не в коде: docker-сеть `433lab_default` по умолчанию занимает 172.18.0.0/16, а на хосте поднят VPN-интерфейс `singbox_tun` с адресом 172.18.0.1/30 — диапазон пересекается. Контейнеры после передеплоя получили 172.18.0.2 (backend) и 172.18.0.3 (web), и оба адреса недостижимы: `.2` перехватывается правилом `from all to 172.18.0.0/30 lookup 2022` и уходит в туннель (`default via 172.18.0.2 dev singbox_tun`), а `.3` — это broadcast-адрес сети /30, для него ядро завело `broadcast 172.18.0.3 dev singbox_tun table local`, и таблица local смотрится первой (приоритет 0). Симптомы сходятся: на самом сервере `curl 127.0.0.1:6060` даёт connection refused за 1 мс (docker-proxy принимает, но до 172.18.0.3 не достучаться), снаружи мультиплексор отдаёт 502. Контейнеры при этом Up, nginx внутри стартовал без ошибок. Это повторение июльской аварии — тогда web стоял на 172.18.0.2 и симптом был таймаут; из /30 (адреса .0-.3) при двух сервисах контейнеры попадают в конфликт всегда, так что баг не плавающий, а гарантированный при поднятом VPN. Фикс: в docker-compose.yml подсеть закреплена явно — `networks.default.ipam.config.subnet: 172.30.0.0/16` (свободна: заняты 172.17-172.23). Применение требует `docker compose down && docker compose up -d --build`, т.к. подсеть существующей сети не меняется на лету; тома `media` и `dbdata` именованные, `down` без `-v` их не трогает.
